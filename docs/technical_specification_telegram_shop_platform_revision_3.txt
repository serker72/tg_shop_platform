ТЕХНИЧЕСКОЕ ЗАДАНИЕ И АРХИТЕКТУРНЫЕ ТРЕБОВАНИЯ
Проект: модульная multi-tenant платформа Telegram-магазинов

Цель документа
----------------
Этот документ предназначен для передачи разработчику на ревизию архитектуры и плана разработки.

Главная задача — не просто добавить новый функционал в существующего Telegram-бота, а перестроить проект в масштабируемую платформу, которую можно долго развивать, безопасно обслуживать и восстанавливать после сбоя/замены бота/сервера.

Ключевые требования:
- модульность;
- понятность кода для нового разработчика;
- возможность добавлять новые функции без переписывания существующей системы;
- поддержка большого количества пользователей и высокой нагрузки;
- возможность одновременно запускать много Telegram-ботов;
- единая бизнес-логика и единая БД для нескольких ботов/зеркал;
- централизованное хранение товаров и медиа;
- минимальная зависимость от Telegram как хранилища файлов;
- полноценные резервные копии и восстановление;
- разграничение прав;
- безопасность;
- тестируемость;
- возможность горизонтального масштабирования.

2. MULTI-TENANT АРХИТЕКТУРА
---------------------------

Необходимо проектировать систему как multi-tenant платформу.

Tenant = отдельный магазин/клиент/пространство.

Пример:

Tenant #1
- Bot A
- Bot B
- товары
- категории
- подкатегории
- пользователи
- заказы
- модераторы
- настройки

Tenant #2
- Bot C
- товары
- категории
- пользователи
- заказы
- модераторы
- настройки

Все tenant'ы могут использовать одну PostgreSQL и одну платформу.

Основные бизнес-сущности должны быть привязаны к tenant_id, где это необходимо.

Важно обеспечить строгую изоляцию данных между tenant'ами на уровне Service/Repository и, при необходимости, дополнительными ограничениями PostgreSQL.

3. MULTI-BOT
------------

Необходимо поддерживать большое количество одновременно работающих Telegram-ботов.

Не создавать отдельный код/папку/приложение под каждого бота.

Нужна сущность Bot:

- id
- tenant_id
- telegram_bot_id
- name
- encrypted_token
- status
- configuration
- created_at
- updated_at
- другие необходимые поля

Нужен Bot Manager, который умеет:
- загружать активных ботов;
- запускать ботов;
- останавливать конкретного бота;
- перезапускать конкретного бота;
- проверять состояние;
- корректно обрабатывать ошибки одного бота, не ломая остальные;
- загружать/обновлять конфигурацию.

Архитектурно:

Bot A \
Bot B  \
Bot C   -> одна бизнес-логика -> PostgreSQL / Redis / MinIO
Bot D  /
Bot E /

Цель — возможность иметь условно 100+ зеркал без копирования бизнес-логики.

4. БЕЗОПАСНОСТЬ ТОКЕНОВ
-----------------------

Bot token нельзя хранить в открытом виде без необходимости.

Желательно:
- шифровать токены;
- ключ шифрования хранить отдельно от PostgreSQL;
- секреты хранить через environment/secrets manager;
- никогда не помещать токены в git;
- исключить токены из обычных логов;
- продумать безопасную ротацию токенов.

Backup базы данных не должен автоматически означать наличие ключа расшифровки токенов.

6. STORAGE / ХРАНЕНИЕ ФАЙЛОВ
----------------------------

Не использовать Telegram file_id как единственный источник хранения товара.

Основное хранение:
MinIO или совместимое S3 object storage на собственной инфраструктуре.

PostgreSQL хранит metadata:

product_media:
- id
- product_id
- storage_key
- mime_type
- size
- width
- height
- checksum
- created_at

Пример:

storage_key:
products/8472/abc123.webp

Один файл должен быть доступен любому боту, который имеет права на соответствующий tenant.

Необходимо сделать абстракцию StorageService, чтобы бизнес-логика не зависела напрямую от MinIO.

Например:
StorageService
- save
- get
- delete
- copy
- exists

Реализация:
- MinIOStorage
- в будущем S3Storage

Это позволит при необходимости перенести хранилище без переписывания бизнес-логики.

7. ПОЧЕМУ НЕ MONGODB ДЛЯ ФАЙЛОВ
------------------------------

MongoDB технически может использоваться для хранения файлов, но для данного проекта предпочтительнее object storage.

Причины:
- правильная модель для больших файлов;
- удобная работа с изображениями/видео;
- проще делать backup;
- проще масштабировать;
- PostgreSQL остаётся БД бизнес-логики;
- storage можно заменить независимо.

MongoDB не требуется только ради хранения медиа.

8. ПРИОРИТЕТ №1 — УСКОРЕНИЕ ЗАГРУЗКИ ТОВАРОВ
--------------------------------------------

Текущая проблема: выгрузка/загрузка товаров может занимать около 30 секунд.

Это нужно исследовать ДО масштабного переписывания.

Нужен profiling текущего процесса.

Нужно замерить отдельно:
- получение данных;
- получение Telegram media;
- скачивание;
- обработку/конвертацию;
- загрузку в стороннее API;
- запись в БД;
- загрузку обратно в Telegram;
- сетевые задержки;
- последовательные операции;
- повторные запросы;
- блокировки.

Цель — получить измеримую картину, например:

download: 1.2 sec
processing: 4.8 sec
upload: 8.1 sec
database: 0.4 sec
telegram: 12.2 sec

После этого исправлять конкретное узкое место.

Не считать, что сама смена архитектуры автоматически решит 30-секундную задержку.

Долгие операции должны по возможности переноситься в ARQ workers.

9. ФОНОВЫЕ ЗАДАЧИ
-----------------

Пользователь не должен ждать завершения большого количества операций.

Например:

Пользователь загружает 100 товаров
  |
  v
Bot
  |
  v
Redis / ARQ
  |
  +-- image processing
  +-- storage
  +-- DB
  +-- preview generation
  +-- notifications
  +-- statistics

Нужны idempotency и защита от повторного выполнения критичных операций.

Например, двойное нажатие "Купить" не должно создавать два заказа.

Можно использовать Redis locks / idempotency keys.

Пользователь может:

- назначить/сменить модератора.

34. BACKUP И RECOVERY

4. migrations
5. настройки системы, которые необходимы для восстановления

Важно:
backup PostgreSQL без backup файлов не является полноценным backup магазина.

Желательно иметь:
- backup на основном сервере;
- backup на другом сервере/хранилище;
- периодические offline/отдельные копии.

Нужен понятный recovery process:

"Чистый сервер -> развернуть Docker -> восстановить PostgreSQL -> восстановить MinIO -> применить migrations/config -> запустить сервисы -> проверить health"

43. КЛЮЧЕВЫЕ ПРИНЦИПЫ КОДА
-------------------------

1. Один модуль отвечает за одну область.
2. Business logic не должна находиться в Telegram handlers.
3. Router должен быть тонким.
4. Service содержит бизнес-логику.
5. Repository отвечает за доступ к БД.
6. Storage abstraction отделяет бизнес-логику от MinIO.
7. Платёжная логика отделена от Telegram.
8. Multi-tenant isolation обязательна.
9. Не использовать глобальные mutable state без необходимости.
10. Критические операции должны быть idempotent.
11. Все финансовые операции должны иметь audit trail.
12. Не хранить секреты в git.
13. Не логировать токены/секреты.
14. Новая функция должна по возможности добавляться новым модулем, а не переписыванием старых.
15. Код должен быть понятен разработчику, который ранее его не видел.
16. Типизация должна использоваться последовательно.
17. Нужны docstrings/comments там, где логика неочевидна.
18. Не допускать "магических" констант и скрытой логики.
19. Миграции должны быть контролируемыми через Alembic.
20. Критическая инфраструктура должна иметь health checks.

45. ИТОГОВОЕ ТРЕБОВАНИЕ
----------------------

Проект следует рассматривать не как "бот с большим количеством функций", а как платформу.

Целевая архитектура:

                    Telegram
                       |
        +--------------+--------------+
        |              |              |
    Generator       Bot A          Bot B ... N
        |              |              |
        +--------------+--------------+
                       |
                  Bot Runtime
                       |
              +--------+--------+
              |                 |
          Service Layer      Events
              |                 |
        +-----+------+         Redis
        |            |           |
    PostgreSQL     MinIO       ARQ
        |
     Telegram Admin

Главный принцип:
одна бизнес-логика -> много Telegram-ботов -> единая БД -> единое object storage.

Основные технические приоритеты:
1. Правильно спроектировать архитектуру.
2. Выявить и устранить причину 30-секундной загрузки.
3. Сделать централизованное хранение файлов.
4. Реализовать multi-tenant.
5. Реализовать multi-bot.
6. Сделать безопасность и backup частью архитектуры с первого дня.
7. Только после этого масштабно добавлять бизнес-функции.

Необходимо получить от разработчика перед началом основной реализации:
- архитектурную схему;
- ER-диаграмму;
- структуру проекта;
- схему multi-tenant;
- схему multi-bot;
- схему storage;
- схему backup/recovery;
- схему permissions;
- план миграции;
- план оптимизации загрузки;
- roadmap реализации;
- описание тестирования.

Цель — получить систему, которую можно поддерживать и расширять годами, а не проект, который работает только до следующего крупного изменения.

46. НОВАЯ РЕВИЗИЯ — ДОПОЛНИТЕЛЬНЫЕ ФУНКЦИИ
============================================================

46.1. ПРОСМОТР НИКОВ РЕФЕРАЛОВ
--------------------------------

В профиле пользователя добавить возможность просмотра его рефералов.

При наличии соответствующего permission администратор/модератор должен видеть:
- список рефералов пользователя;
- Telegram username/ник реферала, если он доступен;
- дату привлечения/регистрации;
- связанную реферальную информацию согласно правам доступа.

Учесть, что у Telegram-пользователя может отсутствовать username.

46.2. ОТЗЫВЫ — ПОДКАТЕГОРИЯ И ПОЗИЦИЯ
--------------------------------------

В каждом отзыве указывать, к какой именно позиции он относится.

В отзыве/карточке отзыва должны отображаться:
- категория;
- подкатегория;
- позиция/Product;
- текст;
- фото/media, если есть;
- дата.

Категория, подкатегория и позиция должны автоматически определяться из заказа/покупки, а не вводиться клиентом вручную.

46.3. «ПРОБЛЕМА С ЗАКАЗОМ» — СПИСАНИЕ
--------------------------------------

При обработке проблемы с заказом добавить выбор стороны, с которой производится списание/компенсация:

- с модератора;
- с клиента;
- с обоих;
- без списания.

Для списания предусмотреть варианты:
- полное списание;
- процентное списание;
- без списания.

Если выбрано «с обоих», должна быть возможность определить долю/процент каждой стороны.

Пример интерфейса:

Списать с:
[Модератора] [Клиента] [Обоих] [Не списывать]

Размер:
[100%] [50%] [25%] [Другой процент] [0%]

Все финансовые действия обязательно фиксировать в BalanceTransaction/ledger и AuditLog/CaseEvent.

Сохранять:
- кто принял решение;
- с кого списано;
- процент;
- сумму;
- причину;
- Case/Order;
- дату;
- связанную финансовую операцию.

Нельзя просто изменять balance без создания финансовой записи.

46.4. ИСПРАВИТЬ ОТПРАВКУ ПРЕДЗАКАЗОВ
-------------------------------------

Исправить текущий баг: сейчас при отправке предзаказа текст и фото приходится загружать/отправлять отдельно.

Предзаказ должен отправляться пользователю одной операцией и восприниматься как единая карточка.

Если конкретный набор данных технически невозможно объединить Telegram API в один физический message, пользовательский flow всё равно должен быть единым: клиент/модератор не должен вручную проходить отдельные шаги для текста и фото.

Текст, фото и остальные данные предзаказа должны обрабатываться совместно.

46.5. ОТЗЫВЫ ДЛЯ ПРЕДЗАКАЗОВ
----------------------------

Добавить возможность оставлять отзывы на предзаказы.

После получения/выполнения предзаказа клиенту должна быть доступна кнопка отправки отзыва.

Предусмотреть кнопку:
«Отправить отзыв о предзаказе»

Если предзаказ содержит фотографии, клиент должен иметь возможность отправить отзыв вместе с фото/media.

Отзыв по предзаказу должен быть связан с:
- конкретным Preorder;
- пользователем;
- позицией;
- подкатегорией;
- заказом/выдачей, если такая связь существует;
- датой.

Система отзывов должна использовать общую модель отзывов, чтобы отзывы обычных покупок и предзаказов можно было анализировать одинаково.

46.6. «ЗАПРОСИТЬ ВЫПЛАТУ» ДЛЯ МОДЕРАТОРА
-----------------------------------------

У модератора добавить кнопку:

«Запросить выплату»

Назначение — запрос выплаты модератору за проданный товар.

Flow:

1. Модератор нажимает «Запросить выплату».
2. Система определяет доступную сумму к выплате или предлагает её подтвердить.
3. Модератор вводит кошелёк для выплаты.
4. Создаётся PayoutRequest.
5. Запрос отправляется Support и Admin на рассмотрение.
6. У согласующих доступны кнопки:
   - Да / Одобрить;
   - Нет / Отклонить.
7. После необходимого/финального одобрения автоматически запускается выплата с нашего кошелька.
8. Модератор получает уведомление о результате.

Рекомендуемые статусы:

PENDING
APPROVED
REJECTED
PROCESSING
PAID
FAILED
CANCELLED

Обязательно предусмотреть:
- защиту от двойного одобрения;
- защиту от повторной выплаты;
- проверку доступной суммы;
- проверку уже выплаченной суммы;
- хранение кошелька;
- сумму;
- комиссию;
- кто одобрил/отклонил;
- дату и время;
- transaction ID/hash;
- ошибку выплаты, если она произошла.

Выплату реализовать через отдельный PayoutService/PaymentService, а не непосредственно в Telegram handler.

Необходимо связать выплату с конкретными проданными товарами/комиссиями модератора, чтобы была прозрачная история:
- что продано;
- сколько начислено;
- сколько уже выплачено;
- сколько доступно;
- какой запрос выплаты это закрыл;
- какая транзакция blockchain соответствует выплате.

46.7. СОЗДАНИЕ РОЛЕЙ И ГИБКИХ РАЗРЕШЕНИЙ
-----------------------------------------

Расширить RBAC.

Администратор должен иметь возможность самостоятельно создавать роли.

Примеры:
- Модератор;
- Суппорт;
- Старший модератор;
- Бухгалтер;
- Менеджер;
- Custom Role.

Роли не должны быть жёстко зашиты в код.

Администратор должен иметь возможность:
- создать роль;
- изменить роль;
- удалить роль;
- назначить роль пользователю;
- снять роль;
- назначить роли нескольким пользователям;
- назначать разрешения роли;
- при необходимости задавать индивидуальные permission overrides;
- посмотреть фактические права конкретного пользователя.

Примеры permissions:

PRODUCTS_VIEW
PRODUCTS_CREATE
PRODUCTS_EDIT
PRODUCTS_DELETE

ORDERS_VIEW
ORDERS_MANAGE

CASES_VIEW
CASES_REPLY
CASES_REFUND
CASES_REPLACE
CASES_CLOSE

USERS_VIEW
USERS_MANAGE
REFERRALS_VIEW

REVIEWS_VIEW
REVIEWS_MANAGE

PREORDERS_VIEW
PREORDERS_MANAGE

PAYOUTS_VIEW
PAYOUTS_REQUEST
PAYOUTS_APPROVE

ACCOUNTING_VIEW
ACCOUNTING_MANAGE

STATISTICS_VIEW
MODERATORS_MANAGE
ROLES_MANAGE
SETTINGS_MANAGE

Проверка permission должна выполняться централизованно через Permission/RBAC Service.

Нельзя использовать жёстко прописанные Telegram ID как основную систему доступа.

Модель:

User
→ Roles
→ Permissions
→ индивидуальные overrides (если используются)

Должна быть возможность определить, почему конкретный пользователь имеет конкретное разрешение: через какую роль или через индивидуальное назначение.

46.8. ОБЩИЕ ТРЕБОВАНИЯ К НОВЫМ ФУНКЦИЯМ
----------------------------------------

Все новые функции должны вписываться в существующую модульную архитектуру.

Рекомендуемые отдельные модули:
- referrals/
- reviews/
- preorders/
- cases/
- payouts/
- permissions/

Использовать:
Router
→ Service
→ Repository
→ PostgreSQL

Финансовые действия:
Service
→ Ledger
→ AuditLog/Event

Критические действия должны иметь audit trail.

Все операции, которые могут повториться из-за двойного клика, webhook или сетевого сбоя, должны быть idempotent.

Новые функции не должны приводить к появлению огромных универсальных handlers или дублированию бизнес-логики.

46.9. ДОПОЛНЕНИЕ К АРХИТЕКТУРЕ СУЩНОСТЕЙ
----------------------------------------

Необходимо предусмотреть сущности/связи:

Referral
ReferralRelationship / ReferralLink

Review
ReviewTarget
ReviewMedia

PayoutRequest
PayoutApproval
PayoutTransaction

Role
Permission
RolePermission
UserRole
UserPermissionOverride (если используется)

CaseResolution / CaseFinancialAdjustment — если это требуется для удобного учёта списаний.

Финальная структура может быть изменена разработчиком после подготовки ER-диаграммы, но все перечисленные бизнес-возможности должны быть поддержаны.

46.10. ДОПОЛНЕНИЕ К ПРИОРИТЕТАМ РАЗРАБОТКИ
------------------------------------------

После базовой архитектуры и оптимизации загрузки отдельно включить в roadmap:

- рефералы и просмотр ников рефералов;
- расширенные отзывы с категорией/подкатегорией/позицией;
- отзывы на предзаказы;
- единый flow отправки предзаказа с фото;
- финансовые списания по кейсам;
- запросы выплат модераторов;
- автоматические выплаты после approve;
- конструктор ролей и permissions.

Все новые функции должны проходить через тесты, особенно финансовые операции, permissions и payout flow.

47. ПОЛНЫЙ ЛОГ КЛИКОВ И ДЕЙСТВИЙ ПОЛЬЗОВАТЕЛЕЙ
============================================================

Необходимо доработать существующее логирование действий пользователей.

Сейчас часть кликов уже отображается/логируется, но информация не сохраняется и лог неполный.

Нужно сделать полноценный persistent audit/click log.

Цель:

Для каждого пользователя иметь возможность восстановить последовательность его действий:

- кто;
- что нажал;
- где находился;
- куда перешёл;
- когда это произошло;
- какой объект был затронут;
- какой бот использовался.

47.1. ЧТО ЛОГИРОВАТЬ

Логировать все значимые пользовательские действия, в том числе:

- нажатие inline/reply кнопки;
- переход в категорию;
- переход в подкатегорию;
- открытие позиции;
- просмотр товара;
- просмотр профиля;
- открытие заказа;
- покупка;
- отмена;
- предзаказ;
- открытие отзыва;
- отправка отзыва;
- открытие обращения;
- сообщения в обращении;
- ответы;
- возвраты;
- нажатие кнопок оплаты;
- пополнение баланса;
- переходы по меню;
- кнопки «Назад»;
- кнопки «Главное меню»;
- подписка на уведомления;
- действия с рефералами;
- действия модератора;
- административные действия;
- ошибки пользовательского flow;
- другие значимые callback/message действия.

Не ограничиваться только callback-кнопками.

Нужно логировать также действия, выполненные через:

- команды;
- текстовые сообщения;
- reply keyboard;
- inline keyboard;
- media;
- Telegram Admin, если действие происходит через него.

47.2. КАКИЕ ДАННЫЕ ХРАНИТЬ

Для каждого события желательно сохранять:

- id события;
- tenant_id;
- bot_id;
- telegram_user_id;
- username на момент события, если доступен;
- тип пользователя/роль, если применимо;
- timestamp с точной датой и временем;
- тип действия;
- название/идентификатор кнопки;
- callback_data, если есть;
- текущий экран/menu state;
- предыдущий экран, если возможно;
- целевой экран/действие;
- entity_type;
- entity_id;
- order_id, если относится к заказу;
- product_id, если относится к товару;
- category_id;
- subcategory_id;
- case_id;
- preorder_id;
- дополнительные безопасные metadata;
- результат действия: success/error/cancelled.

Для времени использовать единый стандарт хранения timestamp, желательно UTC, с отображением в нужной timezone в админке.

47.3. ТЕКСТОВОЕ ХРАНЕНИЕ ЛОГОВ

Помимо хранения в БД необходимо сделать сохранение логов в текстовые файлы.

Логи должны физически сохраняться на сервере, чтобы информация не исчезала после перезапуска бота/процесса.

Рекомендуемый формат:

logs/
  users/
    2026-09-14/
      user_123456.log
      user_789012.log
  bots/
    bot_1/
      2026-09-14.log
  system/
    2026-09-14.log

Либо другой формат, предложенный разработчиком, если он обеспечивает те же возможности.

Для каждого пользователя должен существовать последовательный лог его действий.

Пример строки:

2026-09-14 18:42:31 | bot=17 | user=123456 | username=@example | action=OPEN_PRODUCT | category=5 | subcategory=12 | product=384 | result=success

Следующее действие:

2026-09-14 18:42:38 | bot=17 | user=123456 | username=@example | action=CLICK_BUY | product=384 | result=success

Таким образом можно посмотреть полную последовательность действий пользователя по времени.

47.4. НЕ ТЕРЯТЬ ЛОГИ ПРИ ПЕРЕЗАПУСКЕ

Логирование должно быть persistent.

Нельзя хранить click logs только в:

- RAM;
- Redis;
- временной памяти Python;
- временном контейнерном filesystem.

При использовании Docker необходимо сделать volume для logs.

После:

- перезапуска бота;
- перезапуска runtime;
- обновления приложения;
- падения отдельного bot runtime;

история уже записанных логов не должна исчезать.

47.5. НЕОБХОДИМО ЛОГИРОВАТЬ БОЛЬШЕ, ЧЕМ ПРОСТО «КЛИК»

Важно фиксировать контекст действия.

Например, недостаточно:

user 123 clicked button.

Нужно:

кто → бот → дата/время → экран → кнопка → callback/action → объект → результат.

Это позволит расследовать ситуации типа:

«Что делал пользователь перед покупкой?»
«Во сколько он открыл товар?»
«Сколько раз нажимал кнопку покупки?»
«Переходил ли он в другую подкатегорию?»
«Открывал ли обращение?»
«Какие действия выполнял перед ошибкой?»

47.6. ПОИСК И ПРОСМОТР В АДМИНКЕ

В Telegram Admin/админке предусмотреть просмотр логов пользователя.

Фильтры:

- пользователь;
- Telegram ID;
- username;
- bot;
- tenant;
- дата;
- диапазон времени;
- тип действия;
- product;
- category;
- subcategory;
- order;
- case;
- preorder;
- moderator.

Сортировка:

- новые сверху;
- старые сверху.

Желательно иметь экспорт выбранного лога в TXT.

47.7. ОТДЕЛЬНЫЙ AUDIT LOG ДЛЯ КРИТИЧЕСКИХ ДЕЙСТВИЙ

Click log не заменяет AuditLog.

Необходимо разделять:

1. User Activity / Click Log
   - все пользовательские действия и навигация.

2. Audit Log
   - критические действия, которые влияют на деньги, права, заказы, товары, обращения и настройки.

Например AuditLog должен фиксировать:

- refund;
- payout approval;
- payout rejection;
- изменение баланса;
- списание с модератора;
- списание с клиента;
- выдачу товара;
- замену товара;
- изменение permissions;
- создание/удаление роли;
- изменение товара;
- изменение цены;
- изменение скидки;
- изменение настроек;
- действия администратора.

47.8. ПРОИЗВОДИТЕЛЬНОСТЬ ЛОГИРОВАНИЯ

Логирование не должно заметно замедлять работу бота.

Запись в текстовые файлы желательно выполнять через асинхронный/буферизированный механизм.

При большом количестве событий допускается использовать очередь логирования.

Критически важно:

ошибка записи лога не должна ломать покупку, оплату или другое основное действие пользователя.

47.9. РОТАЦИЯ И РАЗМЕР ЛОГОВ

Предусмотреть:

- разбивку по дням;
- отдельные файлы/директории;
- ротацию;
- ограничение размера;
- архивирование старых логов;
- понятную политику хранения.

Нельзя допускать бесконтрольного роста одного TXT-файла до десятков/сотен гигабайт.

Конкретный срок хранения определить в настройках проекта.

47.10. ВАЖНО ДЛЯ MULTI-BOT

В лог обязательно включать bot_id/идентификатор бота.

Один и тот же Telegram user_id может взаимодействовать с разными ботами/Tenant, поэтому контекст бота и Tenant должен сохраняться.

Система должна позволять ответить на вопрос:

«Что конкретно делал пользователь X в боте Y в промежуток времени Z?»

## 0.5. ФИНАЛЬНОЕ РЕШЕНИЕ ПО ИНТЕРФЕЙСУ АДМИНКИ

**Веб-версию делать НЕ нужно.**

Вся пользовательская, модераторская, саппортская и административная работа должна выполняться **внутри Telegram**.

Требования:
- отдельный Telegram Admin/Web Panel не разрабатывать;
- не делать отдельный браузерный интерфейс для админки;
- админские функции реализовать через Telegram Admin Bot / Admin interface;
- модераторские функции реализовать внутри Telegram;
- Support функции реализовать внутри Telegram;
- управление ролями и permissions — внутри Telegram;
- просмотр статистики — внутри Telegram;
- просмотр логов действий пользователей — внутри Telegram;
- работа с заказами, кейсами, выплатами, балансами, отзывами, предзаказами, товарами, категориями, скидками и настройками — внутри Telegram;
- все права доступа проверять через централизованный RBAC/Permission Service независимо от Telegram-интерфейса;
- Service Layer, Repository Layer, StorageService, PaymentService и остальные backend-компоненты не должны зависеть от конкретного Telegram UI.

### Важное архитектурное правило

Telegram-интерфейс является только способом взаимодействия с системой.

Архитектура должна оставаться:
**Telegram Router/Handler → Service Layer → Repository → PostgreSQL**

Это позволит в будущем при необходимости добавить другой интерфейс без переписывания бизнес-логики, но **в текущем проекте никакую веб-админку реализовывать не требуется**.
